# План переноса Techguns

Дата исследования: 2026-09-07. Это план полного переноса, а не заявление о готовности мода.

## 1. Цель и исходная точка

Сохранить узнаваемое поведение Techguns: оружие, анимации, боеприпасы, броню,
станки, энергию и жидкости, мобов, структуры, прогрессию и серверную игру.
Сначала довести до соответствия оригиналу одну платформу. Следующие платформы
подключать к общей логике только после её проверки.

- Официальная страница: https://www.curseforge.com/minecraft/mc-mods/techguns
- Исходники: https://github.com/pWn3d1337/Techguns2
- Зафиксированный оригинал: `5c95a5b6d79f5adb08096dae39c6307e72b87d64`.
- Оригинальная платформа: Minecraft 1.12.2, Forge 14.23.5.2807, Java 8.
- Объём: 761 Java-файл, 103043 строки Java, 2133 файла ресурсов.
- Рабочий форк: https://github.com/PozziTiv4ik/Techguns2
- Ветка разработки: `port/26.2-neoforge`.

Лицензия остаётся исходной: `LICENSE.txt`. Она отдельно ограничивает выпуск
изменённых версий без разрешения авторов. Форк ведётся как разработка для
возможного вклада в исходный проект. Публикация релизов на CurseForge/Modrinth,
GitHub Releases и распространение сборок требуют разрешения авторов.
Разрешение не считается полученным из факта публичности исходников.

## 2. Выбор платформы

По официальному манифесту Mojang на дату проверки стабильная Java Edition —
**26.2**, текущая предварительная — **26.3-pre-2**. Основная цель:
**Minecraft 26.2 / NeoForge 26.2.0.81 / Java 25**.
Версии зависимостей фиксируются, автоматический выбор `latest` в сборке запрещён.

| Платформа | Решение | Условие включения в поддержку |
|---|---|---|
| 26.2 NeoForge | Основная реализация | Все этапы и проверки ниже |
| 26.1.2 NeoForge | Следующий кандидат | Подтверждённый спрос и отдельная сборка/матрица тестов |
| 1.21.1 NeoForge | Кандидат для старых сборок модов | Адаптер Java 21 и проверка отличающихся API |
| 26.2 Fabric | Возможный второй загрузчик | Измерить долю общей логики после завершения NeoForge |
| 26.3 snapshots/pre-releases | Экспериментальная проверка позже | Стабилизация Minecraft и загрузчика |
| Forge и прочие версии | Не заявлены | Отдельное техническое решение и проверки |

26.2 выбрана по актуальности и наличию официального MDK. NeoForge уменьшает
расстояние до исходной архитектуры Forge. Один JAR не обещает совместимости со
всеми этими версиями. Пустая директория или успешная компиляция не означают поддержку.

## 3. Единая структура

```text
legacy/1.12.2/              исходные Java, ресурсы и старые build-файлы
core/                      логика без импорта Minecraft/NeoForge
platforms/neoforge-26.2/    регистрация, компоненты, сеть, мир, клиент
content/                   отслеживаемый каталог исходного контента и статусов
tools/                     воспроизводимый аудит, генерация, проверки
docs/                      план, решения, инструкции, протоколы проверок
.github/workflows/         компиляция и проверки без публикации релизов
gradle/ + gradlew*         зафиксированная современная сборка
```

`legacy` сохраняет оригинал для сравнения и не входит в новую компиляцию.
Общее ядро содержит состояние оружия, расчёты и правила, которые действительно
не зависят от загрузчика. Сущности Minecraft и графика остаются в адаптере.
Не создавать абстракции для гипотетических платформ до появления второго адаптера.
Ресурсы подключать выборочно и проверять: старые JSON и Java-модели не становятся
современными от копирования в новый JAR.

## 5. Порядок работы и управление рисками

Критический путь: M0 → M1 → M2/M3 → M4/M5 → M6/M7 → M8/M9/M10 → M11/M12 → M13/M14.
Сначала полный проверяемый цикл для одного представителя системы, затем остальные
элементы этой системы. Пример: один работающий станок с персистентностью и
автоматизацией до массового добавления всех станков.

Основные риски: удалённые Forge API, legacy coremod/ASM, старый OpenGL renderer,
изменение форматов моделей/пакетов/рецептов, metadata flattening, transfer API,
изменение миров и недоступные старые интеграции. Механическая замена импортов
эти риски не решает. Ошибки исправляются на уровне поведения и проверяются.

Полный объём не оценивается числом переименованных файлов или количеством JAR.
После первого рабочего цикла каждой крупной системы можно уточнять трудоёмкость.
Срок «за один запуск» для всего исходного объёма не обещается.

## 6. Правила статусов

- `not_started`: существует только исходный код/запись каталога.
- `in_progress`: реализация ведётся; работоспособность не заявляется.
- `implemented`: код готов, обязательные проверки ещё не закончены.
- `verified`: есть воспроизводимая проверка и её результат.
- `deferred`: сознательно отложено с причиной и последствием.

Сборка без ошибок подтверждает компиляцию, но не эквивалентность старому моду.
Отсутствующая система остаётся видимой в плане. Запрещено называть весь мод
перенесённым по результатам одного оружия, одного теста или пустого каркаса.
