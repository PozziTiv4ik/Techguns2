# Порядок продолжения переноса

Это постоянный порядок работы по просьбе владельца проекта. Текущая точка
продолжения находится в [HANDOFF.ru.md](HANDOFF.ru.md); ограничения — в
[AGENTS.md](../AGENTS.md). Числа прошлых прогонов не являются обязательными
ожиданиями для будущих версий: их нужно измерять заново после изменения кода.

## Начало нового чата

Запрос «продолжай» означает: выбрать следующий законченный срез из handoff
и довести его до проверенной реализации в существующем форке. Не ограничиваться
обещанием, планом или первым компилирующимся каркасом. Не запрашивать повторное
разрешение на обычные действия внутри указанного в AGENTS.md объёма работ.

В начале проверить рабочее дерево, ветку, последние коммиты и адреса remotes:

```powershell
git status --short --branch
git log -6 --oneline
git remote -v
```

При сетевой доступности проверить состояние `origin` и последний CI нужного
source commit. Если есть незавершённая работа или красный CI, сначала разобраться
с ними. Не перезаписывать чужие изменения и не переключать ветку вслепую.
Новый worktree нужен только при реальной необходимости изоляции; обычное
продолжение ведётся в существующем checkout `port/26.2-neoforge`.

Читайте summary и следующий этап в [STATUS.ru.md](STATUS.ru.md), нужный этап
[PORTING_PLAN.ru.md](PORTING_PLAN.ru.md) и последний соответствующий раздел
[VERIFICATION.ru.md](VERIFICATION.ru.md). Полную многотысячную историю каждый
раз перечитывать не требуется. Если handoff устарел, исправить его по Git,
исходникам и журналам; не повторять уже завершённую работу.

## Где находится реализация

| Путь | Назначение |
|---|---|
| `legacy/1.12.2/` | Неизменяемый оригинал: поведение, параметры, модели и данные |
| `core/src/main/java/techguns/core/` | Общие правила без Minecraft; тесты в `core/src/test/` |
| `platforms/neoforge-26.2/src/main/java/techguns/modern/` | NeoForge, серверная логика, клиентский код и игровые проверки |
| `tools/legacy_*.py`, `tools/generate_weapon_content.py` | Воспроизводимое извлечение и преобразование оригинала |
| `content/`, `platforms/neoforge-26.2/src/main/resources/` | Каталоги и ресурсы; сгенерированные файлы менять через генератор |
| `tools/tests/` | Проверки соответствия оригиналу и преобразованных данных |
| `tests/worldgen-packs/`, `tests/chemistry-packs/` | Данные выделенных тестовых серверов; не включать в мод |
| `.github/workflows/verify.yml` | Полная Linux-проверка при push в `port/**` |
| `.tools/` и Gradle `build/` | Локальные инструменты, отчёты и кэш; игнорируются Git |

Для нового среза восстановить фактическое поведение оригинала: активные ветки,
metadata, диапазоны RNG, веса, сохранение, ограничения и зависимости. Комментарий
исходника может расходиться с исполняемым кодом. Не заменять отсутствующую
механику декорацией и не перераспределять веса ещё не перенесённых кандидатов.
Использовать уже существующие общие правила и ресурсы, когда они подходят.

## Проверки реализации

Сначала выполнить адресные проверки нового поведения и исправить найденные
ошибки. Проверки должны покрывать последствия для игры: сохранение, загрузку,
границы чанков, повороты, настоящие события/предметы/рецепты, когда это относится
к срезу. Не писать тесты только ради увеличения счётчика.

Перед первым коммитом обычного среза выполнить полный набор, соответствующий CI.
Следующие команды запускаются из корня, каждая должна завершиться с кодом 0;
при ошибке остановиться и исправить причину, а не продолжать список вслепую.

```powershell
python tools/audit_legacy.py --check
python tools/generate_weapon_content.py --check
python -m unittest discover -s tools/tests -v
python tools/verify_resources.py
powershell -NoProfile -File tools/dev.ps1 build --no-daemon --console=plain
powershell -NoProfile -File tools/dev.ps1 :neoforge-26.2:runGameTestServer --no-daemon --console=plain
powershell -NoProfile -File tools/dev.ps1 :neoforge-26.2:runOreWorldTestServer --no-daemon --console=plain
powershell -NoProfile -File tools/dev.ps1 :neoforge-26.2:runChemistryTestServer --no-daemon --console=plain
git diff --check
```

`tools/dev.ps1` использует `JAVA_HOME` либо единственный JDK в `.tools/jdk25`.
Нужен Java 25; после свежего клонирования локальной `.tools/` может не быть.
На Linux/macOS использовать `./gradlew` с теми же задачами. Версии зависимостей
брать из `gradle.properties` и Gradle-файлов; не обновлять платформу попутно.

Серверные прогоны запускать последовательно. Журналы сохранять под понятными
именами в `.tools/`, отмечать время и реальные коды выхода. Не менять исходники
или ресурсы во время прогона. Для адресного запуска через `--args` сохранять
главный класс `net.neoforged.fml.startup.GameTestServer`; для worldgen также
сохранять `--packs`, `--universe` и нужный фильтр, как в Gradle-конфигурации.

Python можно разбить на независимые пакеты, если это оправдано: сохранить
списки test ID и доказать, что их объединение без повторов равно полному
`unittest discover`. Пропуски, потерянные пакеты и один успешно завершившийся
пакет не равны полному успеху. Не повторять уже прошедшие проверки без новых
изменений или конкретного сомнения.

Итоговые числа брать из JUnit XML `core/build/test-results/test/`, Python-отчёта
и строк `GAME TESTS COMPLETE` / `All ... required tests passed` серверных журналов.
Различать основной, worldgen и условный серверы; встроенный тест Minecraft
учитывать отдельно от тестов Techguns. Проверять ошибки загрузки данных и коды
завершения, а не только последнюю строку журнала.

При изменении содержимого/сборки сверить ресурсы JAR с результатом
`generate_weapon_content.generate()`, лицензию с `LICENSE.txt`, исключение legacy
и тестовых паков. Не сравнивать размер JAR как доказательство правильности.
Дерево `legacy/1.12.2/src` должно оставаться
`270b27b1cc52019733bb79facda68ce29aa038be`; дополнительно проверить Git diff
всей `legacy/1.12.2` относительно начала работы.

Для задачи только про документацию достаточно проверки ссылок, указанных
команд/путей, согласованности текущего состояния и `git diff --check`.
Полную игровую регрессию заново не запускать и не выдавать старые результаты
за новые. Изменения генератора, Gradle, CI или тестовых паков не относятся
к этому исключению.

## Два коммита и два пуша для обычного среза

1. После локальных проверок обновить затронутые docs, план, статус и handoff.
   Указать, что Linux CI нового кода ещё ожидается. Просмотреть diff, включить
   только свои изменения, сделать содержательный коммит и push в
   `origin port/26.2-neoforge`. Запомнить полный SHA source commit.
2. Найти запуск `Verify development port` именно для этого SHA, дождаться
   завершения и прочитать результат. При падении изучить логи, исправить
   причину, повторить затронутые проверки и отправить исправление. Номер
   workflow и число шагов получать от GitHub, а не вычислять из прошлого номера.
3. Только после успеха записать SHA, ссылку/номер CI, дату, реальные количества
   тестов и ограничения в verification/status/handoff. Сделать второй коммит
   только документации с `[skip ci]` и второй push. Если в него попало изменение
   кода/ресурсов/сборки, это уже новый source commit: ему нужны проверки и CI.
4. Проверить, что remote содержит итоговый HEAD, собственных незакоммиченных
   изменений не осталось, а изменения после проверенного SHA — только docs.
   Существовавшие чужие изменения сохранить и явно отметить.

Это два разных результата: проверенная реализация и подтверждение CI.
При исправлениях коммитов может быть больше; для документации — меньше.
Не делать пустые коммиты, не отключать тесты, не скрывать ошибки и не использовать
force-push ради заданного количества. Публикация исходников в форке не означает
разрешения выпускать бинарный релиз.

Для `gh` всегда указывать форк, потому что `upstream` ведёт к оригиналу:

```powershell
$sourceCommit = git rev-parse HEAD
gh run list --repo PozziTiv4ik/Techguns2 --commit $sourceCommit --limit 5 --json databaseId,headSha,status,conclusion,url
```

После получения фактического ID использовать `gh run view` / `gh run watch`
с `--repo PozziTiv4ik/Techguns2`. Сверить `headSha` и логи с source commit;
старый зелёный запуск не подтверждает новый код. Если CI или сеть недоступны,
продолжить независимую работу, а при настоящем блокере оставить точный handoff
с pending-проверками. Не записывать неподтверждённый успех.

Уведомления проверять только по этому форку. Сначала устранить причину ошибки
и проверить исправление, затем отметить обработанное уведомление завершённым.
Не удалять workflow/логи/issue и не закрывать непонятное обращение только ради
пустого списка. Не отправлять сообщения другим людям без отдельного поручения.

## Завершение и передача следующему чату

Handoff — короткая текущая запись, не растущая копия всего журнала. После
каждого среза заменить последний проверенный source commit/CI, незавершённые
действия, следующий срез и полезные точки входа. История доказательств остаётся
в verification; общий прогресс и ограничения — в status и плане.

Ответ пользователю — по-русски, примерно как в предыдущем режиме: что теперь
работает, реальные результаты проверок и ссылка CI, фактическое количество
коммитов/пушей за текущую работу, существенные ограничения и следующий этап.
Не выдумывать процент готовности из количества файлов/тестов и не называть
весь порт завершённым. Визуальные проверки обозначать отдельно от headless.

Инструкции намеренно находятся в корневом `AGENTS.md`: это штатная точка
загрузки правил проекта в Codex. Новый чат нужно открыть именно в этом проекте
с актуальным checkout. Подробности механизма — в
[официальной документации OpenAI](https://learn.chatgpt.com/docs/agent-configuration/agents-md).
Файлы сохраняют рабочие договорённости и состояние, а выбранная модель остаётся
под управлением пользователя; дословное совпадение ответов не требуется.
